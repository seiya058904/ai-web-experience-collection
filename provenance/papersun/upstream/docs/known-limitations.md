## Rendering and physical interpretation

PAPERSUN is a DOM/SVG paper theatre over generated raster environments. Masks, physical-looking SVG foreground props, two image surfaces and registered screen-space transforms create a 2.5D composition. The project does not contain continuous 3D models of the city, bridge, room or character, a camera that can orbit them, or physically simulated paper. The bridge-to-room handoff uses a purpose-generated midpoint plate and a solid arch to join separately authored views. The outdoor bridge does not literally morph into a reconstructed desk mesh. These choices are visible approximations, and the actual transition stills and motion captures remain the basis for their artistic review.

The three sun fragments are code-owned SVG paths with shared interior seam coordinates and exact circular outer arcs. One `#journey-sun` retains those paths between table, sky and repaired opening. That mathematical geometry does not make the generated sky aperture itself analytic: the disc is registered over an irregular raster rim by measured screen coordinates. The AI-07 generated sun is a material/light reference only; its illustrated seam map is not substituted for the canonical repair geometry.

The portrait opening is a separate generated image, not a crop of the desktop opening. Several middle chapters reuse wide environments with responsive registration and live props. Purpose-built portrait SVG stages preserve story objects when art fails. There is not a separately generated portrait background for every chapter. Final ordinary-size and boundary-width evidence shows the tested compositions; it does not prove all possible aspect ratios.

The independent review identified CH-06 and CH-10 as the weakest initial non-hero scenes. Visible fixes include a six-blade fibrous rotor without the black filter artifact, warm material and red stitches on the repaired disc, supported roof contact, correct target-mask endpoints, same-note staging, one bridge arch, opaque rotor exit and safer phone reading surfaces. Historical failures and specific successful retests are retained in [the independent visual record](independent-visual-review.md). A measured bounding-box PASS is not used as an automatic aesthetic PASS.

Production images are quality-88 WebP derivatives. The source includes eight inspectable WebP concepts, the production WebPs, original prompt records and derivative hashes/dimensions. Large PNG/base64 transfer intermediates are not runtime dependencies. The exact distributed asset-integrity result covers 16 WebPs. No externally hosted font, media asset or analytics service is required at runtime.

## Story state and persistence

Discovery and repair are intentionally separate. Visitors may skip chapters and try the repair without first discovering every piece. Placing a piece does not rewrite the discovery inventory. A local scene reset restores the prop while retaining the discovery; Begin again clears the narrative memory. Later chapters show the complete fictional outcome while controls preserve the visitor's own repair state.

If a visitor scrolls into the lifting chapter without assembling the table, the narrative disc takes sole gold ownership at that boundary and the loose table pieces are hidden for the lift. This is a deliberate discrete story-state handoff, not a physically animated automatic assembly and not a saved repair action. Reversing out restores the unplaced table pieces. The labelled `tr09-unassembled` sequences preserve the actual empty `placed` state before and afterward; the separate assembled sequences follow real placement through the controls.

A real desktop discovery→assembly→lift→opening return→Begin again sequence passed: the repaired opening remains visible after a completed repair, and restarting restores the original absence. Touch-mobile actions also complete all three discoveries and the repair/lift. These are observed state results, not a claim that every alternative input technology was tested.

Progress storage is local to the browser origin/profile. It is not a cloud account, synchronization service or cross-device save. Blocked/corrupted storage retains the story but can prevent persistence. There is no backend or service worker. The tested offline case starts with already-warmed images; the app does not promise a fully offline first visit or unlimited offline resource retention.

## Browser, device and accessibility scope

The final isolated suites use Playwright 1.62.1 with Chromium 153.0.8010.0 on Linux, CPU rasterization and a custom test executable outside the app dependency tree. Browser binaries and private profiles are not shipped. The normal reproducible optional suite uses the browser installed by `npx playwright install chromium`; that may be a different revision than the build session's custom binary. [The environment record](browser-qa.md) explains the managed-route failure, initial Fontconfig error and corrected runtime.

Full reading/state matrices cover 1440×900 desktop and 390×844 emulated touch-mobile profiles at DPR 1. Selected risk states cover all eight required CSS sizes, breakpoint neighbors and short landscape. Real CDP touch scrolling and Playwright touch taps were executed; these are input emulation, not a physical Android or iOS device. A 3840×2160 CSS viewport is not proof of a 4K monitor, and screenshot scaling is not browser zoom.

**NOT TESTED:** Safari/WebKit, Firefox, native Windows browser execution, physical Android/iOS devices, dynamic phone browser chrome, hardware safe areas, a software keyboard, high-refresh-rate displays, actual speaker output and assistive-technology user sessions. Native Windows `.cmd` launcher execution is also untested. No WCAG conformance certification or universal engine compatibility claim is made.

Actual tested access includes real selectable English DOM, all eleven text-edition sections, visible focus in inspected controls, chapter/About access, dialog Tab/Escape and opener restoration, focused-button Space activation, named piece buttons and reduced-motion outcomes. These checks do not replace a complete screen-reader audit or the blocked browser capabilities.

## Recovery and performance interpretation

There is no runtime WebGL renderer. Unsupported WebGL or a lost WebGL context is **not applicable by architecture**, not a claimed experimentally passed graphics fallback. Relevant risks were exercised through image 404s, target-owned SVG fallback, retry, late fonts, out-of-order image completion, resize, storage failure and lifecycle freeze/resume.

The local `?test-assets=slow` diagnostic adds `qa-delay` to image URLs. `scripts/serve.mjs` asynchronously delays only `/art/` image responses and clamps the delay to 0–5000 ms. This simulates response latency and completion ordering; it is not constrained bandwidth or a real mobile connection. A separate actual Chromium network-emulation case used cache disabled, 96 KiB/s download, 48 KiB/s upload and 150 ms latency and preserved a newer target despite late images. Neither test establishes physical-network or low-end-phone performance.

Continuous media is captured from actual Chromium compositor frames during motion, with frame timestamps, native scroll offsets and rAF observations. Animated WebPs are encoded from those observed frames with observed intervals. They are not animations of separately sought quarter states. The capture method, CPU renderer and recording overhead affect timings. Some final local suites ran concurrently on separate loopback ports, so those observations are not controlled before/after performance comparisons. rAF intervals are not a monitor's displayed FPS.

The report contains measured local first-art/hero/living-hold timings, actual click-response observations, LCP candidates and long tasks. It does not contain a controlled hardware benchmark, a Lighthouse score, field INP/CLS, a physical-device result or a guaranteed 60/120 FPS claim. The estimated JavaScript heap is rounded to 10,000,000 bytes before and after the observed round trip; that coarse Chromium-only reading is not proof of no leak, whole-process memory stability or indefinite operation.

Sound begins off and enabling it requires a gesture. Its control and Web Audio enable/disable path were exercised, but the headless run was not listened to. Speaker loudness, audible quality, routing, actual audio-device failure and hidden-tab sound restoration are **NOT TESTED**. Source review confirms short bounded procedural voices, immediate silencing/stopping on disable and no additional recurring animation clock or external samples.

## Development and handoff

The production app does not use hot module replacement. Vite development cleanup removes the ticker and destroys Lenis, renderers and audio, but some anonymous document/window/media listeners survive a hot replacement. Use a full reload after interactive source edits. This development limitation does not imply that normal production chapter navigation repeatedly installs listeners.

The default preview/development hosts and both launchers bind 127.0.0.1. `HOST` and `PORT` may be intentionally overridden. Running the included server is a local action, not deployment. The Linux launcher smoke with installed dependencies passed; native Windows execution remains untested. The source workflow uses Node 24+ and the lockfile. Included `dist/` also supports a Node-only prepared preview without installing npm dependencies.

The source archive preserves all stills, failure reports and review history. It may omit raw JPEG folders only for completed continuous sequences whose matching animated WebP and complete original frame/timing JSON are retained. The package manifest lists every omitted raw path and its replacement animation/metadata. The JSON continues to record original frame filenames; those are capture-origin references and may not resolve inside the curated ZIP. No raw working capture is deleted, and no broader historical-still omission is applied.

One state-still filename collision is explicitly disclosed: the original `local-carrier-final` empty-state matrix's plain quarter/neighbor image names were reused by the later collected-state capture. Its report marks those links `SUPERSEDED_LINKS`, preserving the measurements without misrepresenting the current pixels. The separate `local-carrier-baseline-layout-2026-11-09T09-51-29-976Z.json` rerun has 140/140 passing measured cases and unique empty-state image names. The uniquely named motion clips and all-frame contacts were unaffected. Future collected stills receive a `-collected` suffix.

Machine-specific absolute paths in 35 text evidence files were normalized in two recorded batches.
